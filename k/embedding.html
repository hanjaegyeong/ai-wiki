임베딩

Embedding

텍스트, 이미지, 코드 등을 의미를 담은 숫자 벡터로 변환하는 기술. "자동차"와 "automobile"이 벡터 공간에서 가까이 놓여, 의미 기반 검색과 비교가 가능해진다.

의미를 좌표로 바꾼다

"자동차"와 "automobile"은 글자 하나 겹치지 않지만 뜻은 같다. 컴퓨터에게 이 사실을 알려주는 방법이 임베딩이다. 임베딩 모델은 텍스트를 수백~수천 개의 숫자로 이루어진 벡터로 변환하는데, 이 변환의 핵심 성질은 의미가 비슷할수록 벡터가 가까워진다는 것이다. 지도 위에서 가까운 두 점이 실제로 가까운 장소이듯, 의미 공간에서 가까운 두 벡터는 비슷한 이야기를 하고 있다. 얼마나 가까운지는 코사인 유사도 같은 간단한 수식으로 계산하므로, "이 두 문장이 같은 얘기인가"라는 어려운 질문이 "두 벡터의 각도가 몇 도인가"라는 쉬운 계산으로 바뀐다. 텍스트만이 아니라 이미지, 코드, 음성도 같은 방식으로 벡터화할 수 있고, CLIP 계열처럼 이미지와 텍스트를 한 공간에 넣으면 "노을 지는 바다"라는 문장으로 사진을 검색하는 것도 가능해진다.

검색이 임베딩으로 바뀌는 과정

임베딩이 가장 많이 쓰이는 곳은 RAG 파이프라인이다. 순서는 이렇다. 먼저 사내 문서를 적당한 크기로 쪼개고(청킹), 각 조각을 임베딩 모델에 통과시켜 벡터로 만든 뒤 벡터 DB에 저장해 둔다. 사용자가 질문하면 그 질문도 같은 모델로 벡터화해서, DB에서 가장 가까운 벡터 몇 개를 찾아 원문 조각을 꺼낸다. 이 조각들을 LLM의 컨텍스트에 넣어주면 모델이 근거를 보고 답한다. 키워드가 아니라 의미로 찾기 때문에 "파이썬 리스트 정렬"로 검색해도 "Python list sort"를 다룬 문서가 걸린다. 코드로는 API 한 줄이다. OpenAI의 text-embedding-3-large에 텍스트를 보내면 최대 3,072차원 벡터가 돌아오고, 이걸 Pinecone이나 pgvector에 넣으면 끝이다. 추천 시스템, 중복 문서 탐지, 이상 로그 감지도 결국 "벡터가 가까운 것을 찾는다"는 같은 원리의 변주다.

어떤 모델을 고를까

2026년 현재 선택지는 크게 셋이다. API형으로는 OpenAI text-embedding-3, Google의 Gemini Embedding(MTEB 다국어 리더보드 상위), 검색 품질에 특화된 Voyage 계열이 대표적이고, 직접 서빙하려면 Qwen3-Embedding 같은 오픈 웨이트 모델이 벤치마크 상위권이다. 고를 때는 MTEB 점수만이 아니라 한국어 지원, 차원 수, 비용을 함께 본다. 요즘 모델들은 마트료시카 표현학습을 지원해서, 3,072차원 벡터의 앞쪽 1,024차원만 잘라 써도 품질이 몇 퍼센트밖에 안 떨어진다. 벡터 DB 저장 비용이 차원 수에 비례하므로 실무에서 꽤 유용한 손잡이다. 한 가지 절대 규칙은 색인과 검색에 같은 모델을 써야 한다는 것이다. 모델마다 벡터 공간이 완전히 다르므로, 임베딩 모델을 교체하면 저장해 둔 문서 전체를 다시 임베딩해야 한다.

임베딩이 잘 안 통하는 경우

의미 검색이 만능은 아니다. 에러 코드 E4013이나 제품 모델명처럼 정확한 문자열이 중요한 검색에서는 오히려 전통적인 키워드 검색(BM25)이 정확하다. 그래서 실무 검색 시스템은 대부분 키워드 검색과 벡터 검색을 함께 돌려 결과를 합치는 하이브리드 검색을 쓴다. 청킹 방식도 품질을 좌우한다. 문단을 너무 잘게 쪼개면 맥락이 사라진 벡터가 되고, 너무 크게 자르면 여러 주제가 뭉개진 평균적인 벡터가 된다. RAG의 검색 품질이 낮다면 LLM보다 먼저 임베딩과 청킹부터 의심하는 게 순서다. 정밀도를 더 끌어올려야 한다면 벡터 검색으로 후보 수십 개를 넓게 건진 뒤, 리랭커(질문과 문서를 쌍으로 넣어 관련도를 정밀 채점하는 모델)로 다시 정렬하는 2단계 구성이 정석이다. 임베딩은 문서를 미리 벡터로 만들어두는 대신 정밀도를 조금 양보하는 방식이고, 리랭커는 매번 쌍을 계산해서 느린 대신 정확한 방식이라, 둘을 조합하면 속도와 품질을 함께 잡을 수 있다.

벡터 하나의 생김새

감을 잡기 위해 구체적으로 보면, 임베딩 하나는 [0.023, -0.741, 0.169, ...]처럼 생긴 부동소수점 배열이다. 각 차원이 "긍정적인가", "기술적인가" 같은 사람이 읽을 수 있는 축인 건 아니고, 수백 개 차원이 얽혀서 의미를 분산 표현한다. 문서 100만 건을 1,536차원 float로 저장하면 벡터만 약 6GB가 되는 식으로 규모가 커지므로, 실무에서는 차원 축소(마트료시카)와 함께 각 숫자를 저정밀로 압축하는 양자화(int8, 바이너리)로 저장량과 검색 속도를 조절한다. 검색 자체는 전수 비교가 아니라 HNSW 같은 근사 최근접 이웃(ANN) 인덱스로 이뤄져서, 수억 개 벡터에서도 밀리초 안에 이웃을 찾아낸다.
