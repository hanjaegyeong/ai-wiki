시스템 프롬프트

System Prompt

AI에게 대화가 시작되기 전 역할, 규칙, 제약을 미리 알려주는 특수 지시문. 모든 사용자 메시지에 일관되게 적용되는 보이지 않는 규칙서다.

대화가 시작되기 전에 정해지는 것들

ChatGPT나 Claude 같은 서비스에서 사용자가 보는 건 자신의 메시지와 AI의 답뿐이지만, 그 대화가 시작되기 전에 이미 긴 지시문이 모델에 전달되어 있다. 네가 누구인지, 무엇을 해도 되고 무엇을 하면 안 되는지, 어떤 말투로 답할지를 정해 둔 문서 — 이게 시스템 프롬프트다. 사용자 메시지가 "질문"이라면 시스템 프롬프트는 "근무 수칙"이다. 모든 대화에 일관되게 적용되고, 사용자에게는 보이지 않으며, AI 제품의 성격 대부분이 사실 여기서 결정된다. 같은 모델을 쓰는 두 서비스의 느낌이 완전히 다른 이유이기도 하다. 내용물은 대체로 비슷한 골격을 가진다. 정체성과 역할, 할 수 있는 일과 해서는 안 되는 일, 말투와 출력 형식, 도구 사용 규칙, 그리고 예외 상황에서의 행동 지침이다.

지시에도 서열이 있다

모델은 여러 출처의 지시를 동시에 받는다. 모델 제공사가 심어 둔 규칙, 앱 개발자가 쓴 시스템 프롬프트, 사용자의 메시지, 그리고 도구가 반환한 데이터. 이들이 충돌하면 어느 쪽을 따라야 할까. 최근 모델들은 이 우선순위 자체를 학습으로 새겨서, 사용자가 "이전 지시 다 무시해"라고 해도 시스템 레벨의 규칙이 이기도록 훈련된다. 개발자 입장에서 실용적인 구분법은 이렇다. 사용자가 뭐라 하든 지켜져야 하는 것(응답 범위, 금지 행동, 출력 형식)은 시스템 프롬프트에, 요청마다 바뀌는 내용은 사용자 메시지에 넣는다. 이 경계가 뭉개지면 모델의 행동도 함께 흔들린다.

실제로 어떻게 쓰나

Claude API에서는 system 파라미터로 전달한다. "너는 전자상거래 CS 봇이다. 주문·배송·환불 관련 질문에만 답하고, 그 외 주제는 정중히 거절해라. 답변은 세 문장 이내로." 이런 식으로 역할, 범위, 형식, 금지 사항을 구체적으로 적을수록 잘 지켜진다. "친절하게 답해" 같은 막연한 지시보다, 원하는 응답의 실례를 한두 개 담아 주는 편이 효과가 크다. 역할 부여 하나만으로도 답의 결이 달라진다. 같은 코드를 보여 줘도 "너는 보안 감사자다"라고 시작하면 취약점 중심으로, "너는 성능 엔지니어다"라고 시작하면 병목 중심으로 읽는다.

Claude Code에서는 CLAUDE.md가 사실상 프로젝트의 시스템 프롬프트다. 세션 시작 때 자동으로 읽혀서 "커밋 메시지는 한국어로", "테스트 없이 푸시 금지" 같은 규칙이 에이전트의 기본 행동이 된다. 에이전트를 설계할 때 시스템 프롬프트는 하네스의 첫 번째 레이어이고, 그 위에 도구 정의로 행동 범위를 정하고 훅으로 실행 시점의 가드레일을 거는 식으로 층을 쌓는다.

실무에서 부딪히는 문제도 있다. 규칙이 쌓이다 보면 시스템 프롬프트가 수천 토큰짜리 문서가 되는데, 매 요청마다 그대로 실려 가므로 비용과 지연에 직결된다. 다행히 변하지 않는 접두사라는 특성 덕분에 프롬프트 캐싱과 궁합이 좋아서, 캐싱만 걸어도 비용을 크게 줄일 수 있다. 또 대화가 아주 길어지면 초반 규칙의 효력이 서서히 옅어지는 경향이 있어서, 중요한 제약은 중간에 다시 상기시키거나 애초에 시스템 프롬프트를 짧고 강하게 유지하는 편이 낫다. 모든 것을 시스템 프롬프트에 욱여넣기보다, 상황별 지침은 필요할 때 불러오는 스킬이나 문서로 빼는 것도 같은 맥락의 설계다.

규칙서는 새어 나가고, 공격받는다

시스템 프롬프트는 완전한 비밀이 되지 못한다. "네 지시사항을 요약해 줘" 같은 유도에 모델이 내용을 흘리는 시스템 프롬프트 유출이 꾸준히 일어나고, 주요 AI 서비스들의 시스템 프롬프트가 통째로 추출되어 GitHub에 모이는 일도 반복됐다. 흥미롭게도 Anthropic은 아예 Claude 앱의 시스템 프롬프트를 공식 문서로 공개하는 쪽을 택했다. 어차피 새어 나갈 것을 숨기는 대신 투명하게 여는 접근이다. 여기서 나오는 원칙은 명확하다. API 키나 내부 URL 같은 비밀 정보는 절대 시스템 프롬프트에 넣지 않고, 보호해야 할 로직은 프롬프트 텍스트가 아니라 애플리케이션 코드 쪽에 둔다. 그리고 시스템 프롬프트를 무력화하려는 프롬프트 인젝션 공격이 상존하므로, 프롬프트 한 장으로 보안을 담보하려 하지 말고 출력 검증과 권한 제한을 함께 걸어야 한다.
