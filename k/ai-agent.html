AI 에이전트

AI Agent

목표를 주면 스스로 계획을 세우고, 도구를 사용하고, 결과를 보고 다음 행동을 조정하는 자율적 AI 시스템.

질문에 답하는 AI와 일을 끝내는 AI

일반적인 챗봇은 질문 하나에 답 하나를 내놓고 끝난다. 에이전트는 다르다. "이 버그 고쳐줘"라는 목표를 주면 그걸 달성하기 위해 스스로 계획을 세우고, 필요한 도구를 골라 실행하고, 결과를 관찰해서 다음 행동을 조정한다. 이 추론 → 행동 → 관찰 루프를 목표가 달성될 때까지 돌리는 것, 그게 에이전트의 본질이다.

여기서 중요한 건 루프의 매 바퀴마다 모델이 환경에서 실제 피드백을 받는다는 점이다. 파일을 고쳤으면 테스트를 돌려 통과하는지 확인하고, 검색 결과가 부실하면 검색어를 바꿔 다시 찾는다. 머릿속으로만 그럴듯한 답을 지어내는 게 아니라, 도구 실행 결과라는 검증 가능한 사실을 딛고 한 걸음씩 나아가는 구조다. 환각이 심하던 초기 모델로는 이 루프가 몇 바퀴 못 가 무너졌지만, 모델의 추론력과 도구 사용 능력이 올라가면서 수십 단계짜리 작업을 완주하는 에이전트가 실용 단계에 들어왔다.

워크플로우로 충분할 때, 에이전트가 필요할 때

모든 자동화를 에이전트로 만들 필요는 없다. Anthropic의 'Building Effective Agents' 가이드는 둘을 명확히 구분한다. 미리 정해 둔 코드 경로를 따라 LLM을 호출하는 건 워크플로우고, 모델이 스스로 경로와 도구 사용을 결정하는 게 에이전트다. "문서를 받아서 유형을 분류하고, 유형별 템플릿으로 요약해라"처럼 절차가 뻔한 작업은 워크플로우가 더 싸고 예측 가능하다. 에이전트가 어울리는 건 경로를 미리 짤 수 없는 작업이다. 원인을 모르는 버그를 잡는 일은 어떤 파일을 열어 봐야 할지 사전에 알 수 없으니, 조사 방향의 결정권을 모델에게 줘야 한다. 가장 단순한 구조로 시작해서 필요할 때만 복잡도를 올리라는 게 이 가이드의 일관된 조언이다.

직접 만들어 보면

가장 단순한 시작은 Claude API에 도구 몇 개를 정의해 붙이는 것이다. 웹 검색, 코드 실행, DB 조회 도구를 등록해 두면 모델이 요청을 보고 필요한 도구를 골라 호출하고, 그 결과를 다음 추론에 반영한다. 이 루프를 밑바닥부터 짜는 대신 Claude Agent SDK 같은 프레임워크를 쓰면 도구 실행, 컨텍스트 관리, 권한 제어가 갖춰진 상태에서 시작할 수 있다. 외부 시스템 연결은 MCP가 표준이 돼서, GitHub이든 사내 DB든 MCP 서버만 있으면 같은 방식으로 에이전트에 붙는다.

매일 쓰는 물건 중에는 Claude Code가 대표적인 에이전트다. "결제 모듈 테스트가 깨졌는데 원인 찾아서 고쳐줘"라고 하면 에러 로그를 읽고, 관련 파일을 탐색하고, 코드를 수정하고, 테스트를 다시 돌려 통과를 확인한 뒤 커밋 메시지까지 써 준다. 사람이 각 단계를 지시하지 않아도 루프가 알아서 굴러가는 걸 그대로 볼 수 있다. 코딩 밖에서도 같은 구조가 반복된다. 여행 일정을 짜 주는 에이전트라면 항공권 검색, 숙소 조회, 캘린더 등록이 도구가 되고, 루프는 동일하다.

혼자보다 여럿이 나을 때

작업이 커지면 에이전트 하나에 모든 걸 맡기는 대신 역할을 나눈다. 오케스트레이터 에이전트가 작업을 쪼개 워커 에이전트들에게 나눠 주고 결과를 종합하는 멀티에이전트 구조가 대표적이다. 각 워커가 독립된 컨텍스트 윈도우를 갖기 때문에, 코드베이스 전체를 뒤지는 조사처럼 한 컨텍스트에 담기지 않는 작업을 병렬로 처리할 수 있다. 다만 에이전트 수가 늘수록 조율 실패 지점도 늘어나므로, 단일 에이전트로 안 되는 게 확인됐을 때 도입하는 게 순서다.

자율에는 청구서가 따라온다

에이전트는 스스로 결정하는 만큼 비용과 위험도 스스로 만든다. 루프를 도는 동안 토큰이 계속 쌓여 단순 호출보다 훨씬 비싸고, 중간에 방향을 잘못 잡으면 그 위에 잘못된 행동이 계속 쌓인다. 그래서 실무에서는 최대 반복 횟수를 정해 두고, 파일 삭제나 외부 전송처럼 되돌리기 어려운 행동에는 사람의 승인을 끼워 넣는다. 보안 관점에서는 비공개 데이터 접근, 신뢰할 수 없는 콘텐츠 읽기, 외부 통신 능력 — 이 셋이 한 에이전트에 겹치면 프롬프트 인젝션 한 방에 데이터가 새어 나갈 수 있어서, 권한을 최소한으로 쪼개는 게 기본기다. 평가도 챗봇과 다르게 접근해야 한다. 답변 문장이 아니라 "일이 실제로 끝났는가"를 봐야 하므로, 최종 상태를 검증하는 테스트를 두고 에이전트가 그걸 통과하는 비율을 재는 식이다. 자율성은 이런 검증 수단이 함께 자랄 때만 늘리는 것이 에이전트를 안전하게 키우는 순서다.
